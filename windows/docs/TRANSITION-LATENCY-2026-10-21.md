# 第3候補の手動確認と第4候補

ユーザーは第3候補で、2画面目がいったん映らず後から表示されたこと、タスクマネージャー上の使用量に改善が見えないことを報告した。「ラグい」のは継続的なパンではなく、起動時と写真の切り替え時、との回答を得た。メモリ・GPU削減や遅延解消を受け入れ済みとは扱わない。既存アプリの終了、操作、設定変更、追加のヒープ／管理者GPU記録は行っていない。

## Windows側の変更

`WindowsPlaybackOutput.PrepareAsync`は写真をworkerでデコードしていたが、背景PNGのハッシュ照合、デコード、色補正、opacity分類は`SharedSceneBuilder.Build`内で表示用dispatcherを占有していた。この経路を`PreparedAmbientTextures.Create`へ分け、写真と同じworkerで処理する。dispatcherへ渡す画像はすべてFreezeし、表示側では準備済みテクスチャからツリーを作る。ツリー作成はBackground優先度で予約し、入力と表示更新を先に処理する。

準備済み背景はそのシーンに保持し、画面再構築・孤立時の繰り返しで再デコードしない。内容一致による画像共有、色補正1回、alpha背景のsource-over、各画面のcropと共有時刻は維持する。通信形式、FPS、写真の解像度、GPUへの提示方法、Mac実装は変更しない。

これはコード上で確認した表示スレッドの作業を移した修正であり、ユーザー環境の遅延全体の主因を実測で確定したものではない。UIツリー構築、GPUへの初回テクスチャ転送、写真の読み込み、同期相手のready待ちなどは残る。

遅延が続いた場合に切り分けられるよう、通常の`app.log`へ次だけを追記する。写真パスや画像内容は記録しない。

- 準備全体が250ms以上: mode、画像数、total／image／ambient／treeの所要時間。totalには待ち時間とdispatcher待ちも含む。
- 切り替えが100ms以上、または開始予定より250ms以上遅れた場合: mode、画面数、既存出力の再利用有無、切り替え処理時間、処理開始時点での予定時刻からの遅れ。

GUI操作なしのWindows回帰14ケースが成功。既存の680出力比較は最大channel差2/255、背景262比較は最大1/255。追加検証ではworkerで作った画像のFreezeと重複共有を確認し、準備後のPNG入力を破壊してからdispatcher上で表示／再構築しても、2画面の色・alpha・fade・終端が参照描画と一致することを確認した。ローカル以外の壊れたPNGを読まないことと準備取消も検証した。入力配列のweak reference検証は引き続き0/24残存。
