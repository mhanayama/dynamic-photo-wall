# 第2候補の実測とGPUトレース

ユーザーは第2候補へ再起動後、「起動直後でも約350MB、スクロール・Pan中のGPUは約5%」と報告した。PID 38956（2026-10-21 09:10:10 JST起動、`memory-candidate2`）を確認し、GPUが改善済みとは扱わず追加調査した。補助PID 3120はタスクバー監視用。

## 通常運転の観測

09:11:59 JSTから30サンプル。3画面・オンライン・背景ON・キャッシュ256MiBの保存条件を維持し、GUI操作、設定変更、ヒープ採取やビルドを計測中に行っていない。

| 指標 | 第2候補の観測 |
|---|---:|
| GPU平均 / p95 / 最大 | 5.89% / 6.18% / 7.51% |
| CPU平均（全16論理コア） | 0.91% |
| Working Set平均（メモリ用30サンプル） | 431.88 MiB |
| Private Bytes平均 | 605.19 MiB |
| GPU Dedicated / Sharedカウンター平均 | 362.92 / 54.56 MiB |

前候補のGPU平均5.91%と比べ、通常再生全体で低下したとは言えない。同一写真・シーン固定のA/Bでもない。メモリの変動は画像準備や切り替えと対応付けていないため、起動直後のユーザー観測値と同一指標・同一時点と扱わない。Working Set、Private Bytes、GPUカウンターは重複を含み、足し合わせない。

生データは`artifacts/windows/gpu-audit/20261021-091159/`と`artifacts/windows/memory-audit/20261021-001159-357-passive/`。

## 管理者権限で取得したETW

通常権限のWPRは`0xc5585011`（プロファイル権限の有効化失敗）で開始できなかった。ユーザーの明示承認後、UAC経由の管理者PowerShellで`windows/scripts/Capture-GpuTrace.ps1 -TargetProcessId 38956 -Seconds 12`を実行した。アプリと設定を維持し、固有名のWPRセッションだけを開始・終了した。取得成功、イベント・バッファ欠落0。記録範囲は09:19:22〜09:19:35 JSTの13.589秒。開始・終了の処理も含む。

`artifacts/windows/gpu-audit/trace-20261021-001921-976/`に`gpu.etl`、`trace-statistics.txt`、`cpu-modules.txt`、`gpu-events.csv`、`gpu-summary.json`を保持する。ETWはシステム全体の情報を含むためローカル保管し、GitやPRへ添付しない。WPRは終了済み。トレースには計測負荷もあり、通常運転の性能基準とは分ける。

本体の`Microsoft-Windows-DxgKrnl/Blit/win:Info`を抽出すると、画面全体をコピーするイベントが2,567回あった。表の頻度は本体イベントの最初から最後までの12.389秒で割ったイベント数で、実際の画面提示fpsとは異なる。

| コピー元領域 | イベント数 | イベント / 秒 |
|---|---:|---:|
| 1920×1080、1画面目 | 823 | 66.43 |
| 1920×1080、2画面目 | 823 | 66.43 |
| 3840×1100 | 921 | 74.34 |

記録された矩形をRGBAの4 bytes/pixelで換算すると合計約2.20GiB/秒の領域に相当する。これはコピー対象領域からの計算であり、実メモリ帯域・PCIe転送量・GPU実行時間の測定値ではない。カーネルイベントだけでWPF内のどのclip、背景、写真がGPU時間の何割を占めたかは特定していない。自作集計でDMA Start/Stopの対応付けは得られず、`DmaExecution`が空なのは解析範囲の限界であって実行時間0ではない。

CPUサンプルでは本体の`wpfgfx_cor3.dll`、`d3d9.dll`、AMDドライバーを確認した。これをGPU時間の内訳へ換算しない。出力は現行のWPF/D3D9経路であり、画面外写真のDrawingを外しても、変化している出力面全体のコピー経路は残っている。次の比較対象は出力面の提示・コピーと全画面合成である、という判断材料になった。これだけでコピーが5.89%全体の原因、またはDX12移行で解決すると断定しない。

解析方法の参照: [MicrosoftのETW／TraceProcessing資料](https://learn.microsoft.com/en-us/windows/apps/trace-processing/tutorial)、[DirectXのプロファイル資料](https://learn.microsoft.com/en-us/windows/win32/direct2d/profiling-directx-applications)。今回は取得・集計にローカルのWPRとxperfを使い、GUI操作は行っていない。

## メモリの内訳と入力バッファの追加修正

全メモリダンプの代わりに、ClrMDのPSSスナップショットから強いGC参照をたどり、画像の寸法とWPFのnative memory pressure推定値を集計した。計測自体のページ読み出しがあるため、取得後のWorking Setを上の受動観測と混ぜない。スナップショットをディスクの全メモリダンプとしては保存していない。診断コード・JSONは`artifacts/windows/memory-audit/candidate2-live/`。

- 09:15:42 JST: ローカルLRUは0 bytes、0エントリー。第2候補の解放は機能していた。2つのGallery計画の画像辞書は18枚と14枚を保持し、RGBA寸法換算で計106.82MiB。WPFの画像native pressure推定は107.75MiB。計画内の先読みや表示終了分を含む保持で、実際の表示枚数とは異なる。managedの到達可能オブジェクトは約40.05MiBだった。
- 09:18:19 JSTの別スナップショット: `BitmapImage.StreamSource`から不要な入力配列へ到達でき、重複を除き19,594,612 bytes（約18.69MiB）が残っていた。managedの到達可能オブジェクトは約26.70MiB、画像native pressure推定は約92.04MiB。いずれも全プロセスやGPUを含む排他的な内訳ではない。

`NetworkBitmap.Decode`は`OnLoad`でデコードしているが、通常の`MemoryStream`をDisposeしても、WPFの`StreamSource`がそのオブジェクトを保持し、内部の入力配列への参照も残る。新しい`ImageDecodeStream`はRead/Seekを転送し、Dispose時に内部ストリームへの参照を外す。配列のコピーや画質変更、デコードの遅延、CPU/GPUの表示頻度変更は行わない。呼び出し側の入力配列のゼロ消去も維持する。

PNG・JPEG・WebP×全8方向の24ケースで、表示用bitmapを保持したままGC後の入力配列をweak referenceで確認した。修正前は16/24件が残存し、修正後は0/24件。入力のゼロ消去と解放後も画素が一致し、読み出せることを確認した。GUIなし回帰13ケース、既存の680出力比較・背景262比較、Gallery仮想2時間・シーン交代・mirrorの検証も成功した。`artifacts/windows/memory-audit/stream-retention/`に結果を保持する。

この追加修正は入力バッファ保持の削減であり、350MB全体やGPU約5%の解消ではない。decoded画像の計画単位保持、WPF・WIC・D3D・出力面のメモリ、提示経路は別途調査が必要。描画APIやFPSを未測定のまま変更せず、Issue #5とGPU監査を継続する。

入力バッファ解放を含むReleaseの単一EXEを`release/windows/win-x64/DynamicPhotoWall.exe`へ更新した。識別用製品バージョンは`0.1.0-memory-candidate3.20261021002729+dbdcaed2268ba011ab66716ed338dcf2c0feeaa4`、SHA-256は`5ca74d8fe668e64939ab1211ac6600452c4c1fdd0655fc9be5d9759791a7ede4`。GUIなしの依存読み込み検証と、ソース差分・ルート生成物なし・発行EXEハッシュを確認。発行時のNuGet脆弱性情報取得警告は残るが、ビルドと検証は成功した。

GPUの提示経路は第2候補から変更していない。旧EXE・BUILD-INFO・チェックサムとビルド記録は`artifacts/windows/memory-audit/stream-retention/release-20261021-002729/`。本体PID 38956と補助PID 3120は維持し、Mac・ZIP・GitHub公開は変更していない。ユーザーの手動再起動後の通常運転で、入力バッファ解放量やPrivate Bytesの変化を検証する。今回のEXEをGPU削減候補とは表示しない。
