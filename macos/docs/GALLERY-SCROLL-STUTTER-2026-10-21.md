# 同期横スクロールの負荷削減（2026-10-21）

ユーザーからネットワーク同期中の横スクロールギャラリーが時々カクつくとの報告を受け、稼働中のMac build 17を調査した。`PNLayerCompositor`で全写真の座標を毎フレーム個別に更新していたため、共通の平行移動を写真列の親レイヤー1個へまとめる修正を加えた。実機でのカクつき解消は未確認。通常アプリ・配布物は更新せず、再起動も行っていない。

## 稼働中アプリの観測

PID 2300、v1.1.0 build 17に8秒の`sample`と20秒指定の`Animation Hitches`を別々に採取した。GUI自動操作、写真・設定・モードの変更は行っていない。

- 8秒の統計スタックではメインスレッド4,773採取点のうち4,394点がRunLoopの待機経路。恒常的なCPU飽和を示してはいない。
- 約21.30秒のトレースでは、メインスレッド946採取点のうち`PNPlayback.render`を含むものが655点、`PNLayerCompositor.update`が509点、`CA::Transaction::commit`が424点。これらは包含関係があり、足し合わせない。Core Animationへの反映処理が主要な経路として現れた。
- 同トレースの33msしきい値の`potential-hangs`は0件。前回の116ms級の計画作成停止や、報告された瞬間の停止を今回の短い採取で再現したとは扱わない。
- `hitches-updates`の通知間隔は実提示フレームの直接計測ではない。今回はその空白を写真の停止時間や欠落率に換算しない。

コード上、横スクロール計画は将来画面へ入る写真も含み、最大128枚を1つのsurfaceに載せる。従来は画面外を含む全写真の位置を更新しており、Core Animationへ送る変更が写真数に応じて増えていた。この不要な変更量を減らすのが今回の修正の範囲であり、観測したカクつきの唯一の原因を特定したという結論ではない。

## 修正と適用条件

`PeerLayerCompositor.swift`で、共通の水平移動・時刻・表示区間を持ち、拡大縮小・独立フェードがなく、各clipが表示画面全体を含む`galleryScroll`を検出する。写真の座標と画像は保持し、共有時計から求めた移動量だけを写真列の親レイヤーへ設定する。背景補間と場面全体のフェードは従来のレイヤーで処理する。

固定の画面clipはscene rootが担当する。写真と一緒に個別clipを動かすと画面へ入る写真を切ってしまうため、この条件下でのみ個別clipのマスクを外す。速度・倍率・表示時刻・フェード・clipが条件に合わない計画は従来の個別レイヤー処理へ戻す。Windows側の計画生成・共有契約、共有時計、ローカル表示経路は変更しない。

## GUI操作なしの検証

`NetworkCompositorTests`へ3件を追加した。

- 128枚・600更新の同じ計画で、従来の個別経路は座標変更76,800回、修正経路は600回。画像の参照と個々の写真座標は保持され、一時停止相当の同時刻更新では追加変更がない。これはレイヤー属性の変更数であり、CPUや提示フレームの改善率ではない。
- 写真の出入り、途中の小数位置、スパン画面のcrop、場面不透明度0.7について、従来の個別レイヤー経路と全画素が一致。整数位置では独立したbitmap描画とも全画素の各channel差4未満を確認する。小数位置の角丸境界には従来からbitmap/レイヤー間のラスタライズ差があるため、修正前後のレイヤーを直接比較する。
- 写真ごとに速度・clip・フェード・開始時刻・倍率が異なる5条件では個別経路を使い、従来と全画素が一致。
